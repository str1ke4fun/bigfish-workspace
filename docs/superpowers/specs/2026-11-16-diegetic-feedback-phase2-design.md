## 1. 目标

本期把她读到的**字**收干净了，但她手上仍然握着一些机械侧的句柄：`permit`、`task_id`、表情 `st_…`、本地路径、坐标。她还要决定「额度够不够」。这些都是机械侧该处理的事。

下期的原则：**她表达意图（对谁说、说什么），机械侧负责一切凭据、绑定、过滤和计数。** 她不需要看见、抄写或带回任何内部句柄。

不是目标：

- 不放松权限类的闸。
- 不改事件流，不让她读台账。
- 不把「只靠提示词约束」当作闸的替代品（§7）。

## 3. 项目一：提醒到点由机械侧投递

**问题：** 到点那一轮，她读到一份 API 调用单，并且手里有一次性密钥。规则本来就是「一个字不许改」，模型在这一步没有增量，只带来泄露和改字的风险。

**方向：** 到点后由插件调用 `sendReminder`，permit 校验保持原样。她在下一轮收到一句世界声，例如「刚才定的提醒已发到「X」」，或失败时「定的那条没发出去」。

**未验证的前提（先查）：**

1. 现在到点靠宿主的 `sch.create({ prompt, after_seconds })` 起一轮模型对话（`remind.js` 约 190–225 行）。插件**能不能收到到点回调**？如果不能，要自己起计时器，那就要处理重启后恢复（`dsh-wx` 的逾期计时器可以参考，但那是另一套持久化）。
2. 到点时她需不需要「知情」？例如她若在到点前一分钟已经手动发过同样的话，机械投递会重复发。要定义去重或取消规则。
3. 到点时微信窗口停在别的会话、树落后、@ 窗口已关：`permit` 只免 @ 和主机闸，名单、频率、当前会话核对照走。机械投递遇到失败时怎么重试、重试几次、最后怎么告诉她，要写清。
4. 失败后是否仍要叫她一轮。叫她就又回到「读到工单」，不叫她就没人知道提醒失败了。

**验收：**

- 到点路径上，她的上下文里没有 `permit`、`chat:`、`text:`。
- 改字不可能发生（她不在链路里），现有「改一个字被拒绝」的测试仍然全绿。
- 重启前定下的提醒，重启后仍会到点（或明确记录为不保证）。

## 4. 项目二：task_id 隐式绑定

**问题：** 25/39 次 `wx_send` 她都带了 `task_id`，说明她在稳定地抄。抄得对不代表该抄：这是机械侧的账。

**方向（比上轮「工具接受会话名」更简单）：**

- `wx_send` 到某会话时，机械侧在任务板里取该会话唯一的活动任务，自动记「回了一半」。
- `task_id` 仍然接受，旧调用不受影响。
- `wx_context`、`wx_task_done`、`wx_task_snooze` 暂不承诺省略 `task_id`；等可靠当前会话语境存在后再改。
- 通知和逾期里不再出现 `t_…`。

**2026-11-17 核实后的修订：**

- 任务板当前只允许同一会话存在一个活动任务；重复来信会追加到同一个任务（`src/dsh-wx/lib/tasks.js` 的 `activeForChat/create`）。因此不存在“多个未回任务选最新还是全部”的产品分支，隐式绑定应取这个唯一活动任务。
- `activeForChat` 的键是 `chatId`，而 `wx_send` 的公开参数是会话名。实施前必须证明能从当前窗口、目录或台账稳定得到目标 `chatId`，并把“会话名 → 当前 `chatId`”写进接口；不能直接把两个字符串硬比。
- `wx_context`、`wx_task_done`、`wx_task_snooze` 没有 chat 参数。在 `exec` 能提供可靠当前会话语境前，它们继续要求 `task_id`；本项只承诺先移除 `wx_send` 的必需句柄。
- 机器绑定失败不能静默记到错误任务；应在结果里保留“任务没记上”的明确状态，并允许调用方带 `task_id` 重试。

**未验证的前提：**

1. “会话名 → `chatId`”在窗口切换、会话改名和目录扫描之间是否稳定；不稳定就不能把自动绑定作为默认路径。
2. `recordReply` 每次调用都会追加一次回复计数；自动绑定必须只在实际发送成功后调用一次，重试和只看到预览的回执要沿用现有三态语义。
3. 她在对话框里被他问了别的事，顺手发了一条给微信某会话，机械绑定会把它记成「回了那个会话的未回任务」。这和现有「主机问话」规则如何区分，仍要在实现设计中写清。

**验收：**

- 不带 `task_id` 的 `wx_send`，任务板记录与带 `task_id` 的一致（对照测试）。
- 带错的 `task_id`（别的会话的）仍然被拒绝，保持现有校验。
- 台账里 `wx_send` 的 `task_id` 使用率下降到接近 0，且没有任务「回了没记」增加。
- `wx_context` / `wx_task_*` 在没有可靠当前会话时仍明确要求 `task_id`，不得因本项自动选错任务。

## 5. 项目三：返回信封化

**问题：** 本期预期失败改成 `ToolError`，只解决了 `Error:` 前缀。返回值仍是字符串，台账和投影靠 render 时反解。

**方向：** 微信工具改成返回 `{ ok, code, ... }` 的对象，由 `wrapTool` 处理，和 QQ、记忆工具一致。

**风险：** `ok:false` 不再是抛错，调用方（逾期、提醒、`sendReminder`）对 `throw` 的处理要全部检查。这是 106 处 `throw` 的完整迁移，不能分批半改。

**前置：** 本期 §7.6 的 `ToolError` 迁移完成，且 `code` 表稳定。

## 6. 项目四：参数面收口

只列要验证什么，不预设结论。

**`wx_click` 的 `x` / `y`**

- 核对结果：`wx_send` 在 `sendToChat` 里自己点击（`run(['click', cx, cy])`，坐标来自它自己读出的界面元素），不经过 `wx_click`，所以移除不影响 `wx_send`。
- 影响的是 `wx_click` 加 `wx_type` 这条手动原语路径：`label` 找不到时没有回退。
- 要先回答：这条原语路径在她的实际使用里还有多少？台账里只有 1 次，样本不够。至少再观察两周，或用 `label` 失败率决定。

**`growth_commit` 的 `confidence`**

- 她在用（10/10），值写进事件，`derive.js` 的信念和观测台在读。
- 移除要先决定：事件里已有的 `confidence` 怎么处理；新写入默认 0.5 还是不写；`derive.js` 读到缺失值是否兼容。
- 这是数据形状变化，必须有迁移和回滚方案，不能作为措辞改动顺带做。

**`qq_napcat_api` 移出目录**

- 先看台账里她是否调用过、调用的 action 是什么。有稳定用途就给那个用途一个单独的人话工具，不把机器接口放回目录。
- 移出会改变可见性矩阵，要同时更新暴露设计文档。

**表情 `st_…`**

- 方向：列表用「第 1 张」，发送接受「第 1 张」或描述。服务端做解析。
- 前置：看 `wx_sticker_*` 现在的参数和台账使用情况。

## 7. 项目五：配额与闸的分层

用户的意图：她想说话时，不要被机械的额度拦下；约束主要放在会话开始时的提示里。

**评估：整体改成「只靠提示词」不可行，按后果分层可行。**

| 闸 | 性质 | 建议 |
| --- | --- | --- |
| 允许名单、主机闸、permit 与原文匹配、换行与长度 | 权限与正确性，发出去收不回 | **保留硬闸** |
| @ 窗口（`mentionWindowMinutes`） | 社交边界：没被叫就在群里说话，别人看得见 | **保留硬闸**，窗口放宽走配置 |
| 每群每日主动额度 | 计数 | **放宽**：超出软上限不拦，台账打标记；保留一个很高的熔断，沿用 `MAX_PER_DAY = 50` 的量级 |
| 发言频率闸（`speechGate`） | 防刷屏 | **保留作熔断**，阈值调到正常对话碰不到 |

**只靠提示词的风险：**

- 提示词管不住循环或失控：一轮里连续发十条，没有任何东西拦。
- 规则段是每次组装时求值的，所以不只在会话开始时；但「剩 2/3」这种数她记不住，也读不到实时值。
- `proactive.js` 的设计原则是「状态记不下来就不发，宁可少说」。纯提示词方案等于放弃这条兜底。

**折中：硬闸只管后果，计数改成事后反馈。**

- 额度超过软上限时放行，台账打标记。
- 下一轮开始时，规则段放一句世界声：「昨天在「X」说了不少，比平时多。」
- 拦下时仍要说清，用本期 §5.4 的世界声，不能 `Error:` 加一整句系统话。

**未验证的前提：**

1. 现在 `decideProactive` 把「没被 @ 且没额度」当成拒绝。放宽后，「软上限」和「@ 窗口」的关系怎么定：超出软上限但窗口内，是放行还是计入？要读 `proactive.js` 剩余部分。
2. 熔断阈值取多少：看她实际每天在各群的发言分布，台账样本现在不够。
3. 用户要不要在工作台里直接调软上限和熔断，还是只调配置文件。

**验收：**

- 权限类闸的现有测试不放宽。
- 超出软上限的发送被放行，台账有标记，下一轮规则段有世界声。
- 熔断触发时，她听见的是一句人话，台账有完整数字。
- `gateRejectRate`（本期已定义）没有上升，且「说了不该说的」没有增加（人工抽查）。

## 9. 项目七：逾期催办的调度

本期只改了催办文案，调度没动：逾期仍然每分钟检查（`index.js:1725` 一带），敲她本身就会让她用受理口吻说话。

方向：第三次之后不再敲；或把催办合并进下一次自然触发的一轮，不单独叫她。

**已核实：** `block` 后任务仍属于活动任务，仍会出现在 `her_inbox` 摘要里，状态显示为“卡住”。因此“第三次后不再敲”不等于任务消失；如果要做合并催办，必须同时决定 blocked 任务是否还进入单独提醒、以及工作台如何提示人工处理。

**前置：** 选择“第三次后静默”“合并到下一次自然触发”还是“只降频”的一种；并确认 `markReminded` 的计数在任务被回复或再次来信后如何重置。

## 11. 排序建议

按风险从低到高，每一项独立验证、独立设计、独立上线、独立回滚：

| 阶段 | 项目 | 进入条件 | 退出条件 |
| --- | --- | --- | --- |
| P0 | 宿主与上下文验证 | 本期阶段 A 开始前 | `ToolError` 呈现、提醒回调、`wx_send` 的名称到 `chatId` 映射、当前会话语境四项都有结论 |
| P1 | 项目七（逾期调度）；项目二（`wx_send` 隐式绑定） | P0 已验证；本期所有新文案已验收 | 催办不再形成高频工单；隐式绑定与显式绑定结果一致，错误绑定可回退 |
| P2 | 项目一（提醒机械投递）；项目五（配额分层） | 提醒回调/重启恢复证明可用；有足够发言分布数据 | 提醒不把 permit 交给模型；软上限只放宽计数，权限类和熔断闸不放宽 |
| P3 | 项目三（返回信封化）；项目四（参数面）；项目六（图片块）；项目八（副本清理） | 各项目独立迁移和回滚方案完成 | 106 处 throw 的调用方全部检查；数据形状变化有回滚；图片/路径降级明确 |

项目三和项目四不能合并成一次“顺手改”：信封化改错误传输，参数面改调用契约，数据迁移和回滚边界不同。项目八可以在任何合适窗口单独做，但必须先迁移测试引用。

## 12. 不做

- 不让她读台账。
- 不把权限类闸交给提示词。
- 不在没有迁移方案时删有数据依赖的参数。
- 不把「看起来像人」当成放开闸的理由。
