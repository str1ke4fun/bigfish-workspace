# 微信下一阶段：请求池、完整群聊上下文与回复台账

状态：设计稿，未实现

日期：2026-11-03

范围：`src/dsh-wx`（微信通道）为主，`src/dsh-fish`（她这一侧）只加最小接口

## 1. 目标

把微信从「看见侧栏里几条 @，合并成一句话递给她」升级成一套**不会丢、不会忘、不会少回、不会回错人**的请求处理系统。

具体目标：

1. **不丢消息**：入站请求先落盘，再处理；宿主重启、模型失败、窗口切走都不丢。
2. **多个请求排队**：按会话排队，全局公平轮转；一个群不会饿死别的群。
3. **分步回复**：一个请求可以回多条，不必一次说完；每条回复都挂在同一个任务上。
4. **不忘记回**：待回任务有状态、有截止时间、有提醒；不依赖模型「记得」。
5. **不少回**：未读数和台账对账；侧栏有新未读但池里没有任务时，自动补任务。
6. **知道是谁在找她**：任务里带群名、发言人、@/私聊/点名证据；识别不了就如实标「未识别」，不猜。
7. **完整会话目录**：侧栏当前页之外，滚动枚举所有会话；长名字解析成全名，不用截断名发送。
8. **完整群聊上下文**：每个群有自己的消息台账，能回看、能按上下文说话；不是只看侧栏预览。
9. **可观测**：工作台能看到队列、待回、逾期、发送结果和失败原因。

非目标（这一阶段不做）：

- 不做微信协议逆向，不接 NapCat 之类的协议端；仍然通过现有 CUA（无障碍树 + OCR + 鼠标键盘）操作客户端。
- 不自动回复所有群聊消息。群里的普通闲聊只进上下文，不自动变成必须回复的任务。
- 不把完整聊天记录直接塞进她的人设或 system prompt。
- 不依赖「多开微信窗口」实现并行。
- 不删除历史消息台账。

## 2. 现状与缺口

### 2.1 侧栏只有当前页

`src/dsh-wx/lib/index.js` 的耳朵每轮只读一次当前可见的侧栏（`look()` / `snapshot()`）。窗口高度决定一次能看到多少行；现在实测大约 9 行。更早的会话要滚动才会出现。

后果：

- 新会话或很久没打开的群，可能永远不进认知。
- 侧栏顺序会变（新消息置顶、置顶会话、时间排序），只靠「这一页」无法建立稳定目录。
- 当前 `seen` 只记录投递过的 key，不记录「微信里到底有多少会话」。

### 2.2 长名字被截断

侧栏和消息区都可能把长群名截成 `星晓家园10号楼13...`。现有 `reconcileChatName()` 只在允许名单里找到唯一前缀时才改写，找不到或撞名就原样返回（`src/dsh-wx/lib/tree.js:109`）。

后果：

- 两个同前缀的群无法区分。
- 台账里记的是截断名，之后想按名字找群、发消息都可能对不上。
- 用截断名做 `includes` 判断有误发风险。

### 2.3 没有完整群聊上下文

当前能拿到的只有：

- 侧栏预览（最后一两行，不是全文）；
- 当前打开会话的消息区，且只保留最近 12 条左右（`wx-elements.mjs` 的 `msgs.slice(-12)`）；
- 没有按会话落盘的消息台账。

后果：

- 她不知道前因后果，只能根据一句预览回话。
- 同一个群连续来几条，她可能只看见最后一条。
- 重启后上下文全丢，无法「接着刚才的话说」。
- 无法回答「谁在找你」「对方刚才说了什么」「这件事进行到哪了」。

### 2.4 消息区没有发言人

无障碍树目前只给消息正文，不给发言人：

```
--- 当前聊天里的消息（从上到下；只有内容，没有发言人）---
消息 "手机" ...
消息 "@D33p53Ek 手机老说自己丢了怎么办" ...
```

侧栏预览有时带发言人前缀，例如：

```
会话 "星晓家园10号楼1302" ... 预览="安卓4224柚厨圣: @D33P533K ..."
```

但这只覆盖最后一条，而且不是稳定字段。

后果：

- 群里不知道是谁在找她。
- 多个人同时说话时，任务归属会错。
- 只能笼统说「群里有人」。

### 2.5 耳朵是「合并通知」，不是任务

现在耳朵会把同一轮命中的所有会话合并成一条 `[微信]` 消息投给同一个微信会话（`src/dsh-wx/lib/index.js:1066`、`:1088`、`:1090`）：

- 一次投递包含多个群；
- 投递成功只记 `seen`，不记「有没有回」「回到哪一步」；
- 没有任务 id，没有状态，没有截止时间；
- 15 秒投递间隔和 45 秒回声保护是节流，不是队列。

后果：

- 她回了一个群，另一个群可能被忘掉。
- 她回了半句，系统不知道这算完成还是没完成。
- 进程重启后，只有 `seen`，没有待办。

### 2.6 她这一侧仍是单会话假设

`src/dsh-fish/lib/identity.js:67` 的 `wakeText` 是全局变量；`src/dsh-fish/lib/store.js:139` 的 `channelOfAgent` 只认一个 `~/.dsh-wx/session.json`。这一阶段继续用**单个微信会话**，不引入多会话并行；但接口要提前留出 `taskId` / `chatId`，避免以后重写。

## 3. 总体设计

```
微信客户端（单窗口）
   │
   ├─ 侧栏扫描器 ──→ 会话目录 ChatDirectory
   │                   （全名、别名、置顶、未读、最后预览）
   │
   ├─ 消息采集器 ──→ 消息台账 MessageLedger
   │                   （每群一个 append-only JSONL）
   │
   └─ GUI Actor ───→ 唯一能点、能打字、能回车的人
                       （全局串行，所有读/写都排队）

侧栏/未读/回复 ──→ 请求池 TaskBoard
                       （new / reading / replying / waiting / done）
                             │
                             ▼
                   单个微信 DSH 会话
                   （只拿到任务摘要 + 绑定到该任务的发送能力）
```

四个原则：

1. **先落盘，再处理。** 入站消息先写台账/任务，再叫模型；模型失败不影响「这条消息存在」。
2. **GUI 单写者。** 所有 `look` / `click` / `type` / `key` / 滚动都由 Actor 串行执行；模型侧不再直接拿原始 CUA 工具做多任务并行。
3. **全名才可发送。** 截断名、别名、未解析名只能用于显示和检索，不能用于发送目标。
4. **任务状态是真相。** 「回没回」看 TaskBoard，不看模型记忆，也不看 `seen`。

## 4. 数据模型

### 4.1 会话目录 `directory.json`

```json
{
  "version": 1,
  "updatedAt": "2026-11-03T15:20:00+08:00",
  "chats": [
    {
      "chatId": "c_7f3a9d2e",
      "displayName": "星晓家园10号楼1302",
      "fullName": "星晓家园10号楼1302",
      "aliases": ["星晓家园10号楼13..."],
      "kind": "group",
      "nameConfidence": "exact",
      "resolvedBy": "current-chat-header",
      "firstSeenAt": "2026-10-21T09:12:00+08:00",
      "lastSeenAt": "2026-11-03T15:08:00+08:00",
      "lastPreview": "安卓4224柚厨圣: @D33P533K 给你充太多大白饭了",
      "lastSender": "安卓4224柚厨圣",
      "unread": 1,
      "pinned": false,
      "position": 2
    }
  ]
}
```

规则：

- `chatId` 在第一次拿到全名后固定；之后改名不换 id，旧名进 `aliases`。
- 未解析的会话用临时 id；解析成功后合并，不创建第二个。
- `nameConfidence`：`exact` / `resolved` / `truncated` / `ambiguous`。只有 `exact` / `resolved` 允许作为发送目标。
- `position` 是最近一次侧栏扫描里的顺序，仅用于展示和滚动恢复，不作为身份。

### 4.2 消息台账 `ledger/<chatId>.jsonl`

一行一条，append-only：

```json
{
  "msgId": "m_01J...",
  "chatId": "c_7f3a9d2e",
  "chatName": "星晓家园10号楼1302",
  "sender": "安卓4224柚厨圣",
  "senderConfidence": "high",
  "direction": "in",
  "kind": "text",
  "text": "@D33P533K 给你充太多大白饭了，现在应该怎么削减",
  "at": "2026-11-03T15:08:00+08:00",
  "capturedAt": "2026-11-03T15:08:06+08:00",
  "source": "tree",
  "dedupeKey": "sha256:...",
  "taskId": "t_01J..."
}
```

字段说明：

- `sender`：群成员显示名；私聊时等于会话名。识别不了写 `null`，`senderConfidence: "unknown"`。
- `senderConfidence`：`high`（树/结构化字段）/ `medium`（侧栏 sender 前缀）/ `low`（OCR）/ `unknown`。
- `direction`：`in` / `out`。她发出去的也要记，才能做「分步回复」和防重复。
- `kind`：`text` / `image` / `sticker` / `file` / `voice` / `system` / `unknown`。
- `at`：微信里能读到的时间；读不到就用 `capturedAt` 并标 `atConfidence: "low"`。
- `dedupeKey`：`chatId + sender + text + kind + 邻接消息摘要`。滚动重叠页靠它去重，不靠时间戳。
- `taskId`：入站消息关联到哪个任务；出站消息关联到哪次回复。

台账不做原地修改。纠正（例如后来识别出发言人）通过追加一条 `type: "repair"` 的记录完成，不覆盖原文。

### 4.3 任务板 `tasks.jsonl`

同样 append-only，记录状态迁移；启动时重放出当前状态：

```json
{
  "taskId": "t_01J...",
  "chatId": "c_7f3a9d2e",
  "chatName": "星晓家园10号楼1302",
  "requester": {
    "name": "安卓4224柚厨圣",
    "kind": "group-member",
    "confidence": "high"
  },
  "reason": "@",
  "status": "new",
  "priority": 50,
  "createdAt": "2026-11-03T15:08:06+08:00",
  "firstInboundMsgId": "m_01J...",
  "lastInboundMsgId": "m_01J...",
  "lastOutboundMsgId": null,
  "replyCount": 0,
  "nextCheckAt": "2026-11-03T15:23:06+08:00",
  "lease": null,
  "attempts": 0,
  "notes": ""
}
```

状态机：

```
new ──claim──→ reading ──first send──→ replying ──finish──→ done
 │                 │                      │
 │                 └── need context ──────┘
 │
 ├── blocked（全名解析失败 / 权限 / 发送失败需要人处理）
 └── waiting（回了，但还在等对方接话；不等于 done）
```

关键点：

- `replying` 允许多次 `send`；每次 `send` 追加一条出站台账，`replyCount++`。
- `done` 只能由 `wx_task_done` 或明确的「这轮不需要再回」规则产生，不能因为「已经发过一条」自动完成。
- `waiting` 仍然出现在待办视图里，但不会每轮催；`nextCheckAt` 到点再评估。
- 逾期：`nextCheckAt` 过了还在 `new` / `reading` / `replying`，标 `overdue`，进入摘要和提醒。
- 失败：发送结果不明确时标 `blocked` + `uncertain`，**不自动重发**。

## 5. 关键流程

### 5.1 完整会话目录

入口：`scanDirectory()`，只在 GUI Actor 空闲时跑，默认每 10 分钟一次，或侧栏摘要变化时触发。

步骤：

1. 快照当前侧栏，记录可见行。
2. 把鼠标移到侧栏空白处，向下滚一页（`wx.sh nudge`），等树稳定，再快照。
3. 重复直到：
   - 连续两页没有新会话名；
   - 或滚动前后摘要完全一样（到底了）；
   - 或达到最大页数（防止死循环）。
4. 回到顶部：向上滚同样页数，或直到摘要与初始页一致；恢复原来的当前会话。
5. 合并进 `directory.json`：
   - 同名同位置：更新未读、预览、最后时间；
   - 新名字：插入；
   - 消失的名字：不删除，标 `lastSeenAt`，保留历史。
6. 对 `nameConfidence != exact` 的项，进入「解析全名」队列。

**全名解析**：

- 点开会话，读 `parsed.current`。如果它不带省略号、且不是截断别名，直接确认全名。
- 如果 `current` 也截断：打开 `Chat Info`，从信息面板/OCR 读完整群名。
- 仍然解析不了：标 `ambiguous`，不进入可发送集合；在待办里显示「名字未确认」，不猜。
- 解析成功后合并临时 id，旧别名保留在 `aliases`。

**注意**：

- 侧栏滚动会改变未读/当前会话；扫描期间暂停耳朵投递，扫完恢复。
- 不要在输入框有草稿时滚动或点开会话；先检查 `parsed.chats[].draft`。
- 不要用「名字前缀包含」做发送目标；只认 `fullName` 精确匹配。

### 5.2 消息台账与上下文采集

入口：`captureChat(chatId, { since })`，由任务 claim 或未读变化触发。

步骤：

1. Actor 点开会话，确认 `current` 是全名。
2. 读当前可见消息区，转成台账候选。
3. 如果可见区第一条不是台账里最后一条，或未读数 > 已采集数：
   - 鼠标移到消息区，向上滚一屏；
   - 等树稳定，读取；
   - 与台账末尾做重叠匹配（`dedupeKey`）；
   - 直到出现重叠、或达到最大回溯页数（例如 20 屏）、或到顶。
4. 回到底部，恢复输入焦点到安全位置（不自动聚焦输入框）。
5. 追加新消息；不覆盖旧行。
6. 更新任务的 `lastInboundMsgId`，把新的入站消息挂到任务上。

**发言人识别**（按优先级）：

1. 结构化树：增强 `wx-elements.mjs`，把消息列表项的子树（发送人、时间、气泡）按坐标/角色输出，配对发言人。当前它明确只输出内容；这是要先补的底层能力。
2. 侧栏预览前缀：`张三: 内容` 只用于最后一条，置信度 `medium`。
3. OCR：在消息气泡上方/左侧识别发送人；置信度 `low`。
4. 都不行：`sender: null`，任务里写「群里有人（发言人未识别）」。

**绝不从正文猜发言人。** 正文里的「张三说」不等于发言人是张三。

**上下文摘要**：

- 给模型的不是整本台账，而是一段受控摘要：
  - 这个群最近 N 条（默认 12 条）；
  - 当前任务相关的入站消息；
  - 谁在问、问的什么、之前她回过什么；
  - 未识别发言人明确标出。
- 更早的内容由 `wx_history(chatId, before/limit)` 按需读取；返回前过 `guard.js` 的 `sanitizeForeign`，不把原始注入文本直接塞进 system prompt。

### 5.3 请求入池

什么算「请求」：

| 来源 | 是否建任务 |
|---|---|
| 私聊未读 | 是 |
| 群里 @ 她 | 是 |
| 群里叫她的名字（trigger） | 是 |
| 回复她上一条消息 | 是（并挂到原任务/原会话线程） |
| 允许名单里的群普通闲聊 | 否，只进台账/上下文 |
| 已有 `waiting` 任务的群又来人 | 是，追加到任务的最新入站，或开子任务 |

入池步骤：

1. 侧栏扫描到未读/新预览，生成候选 `(chatId, preview, unread, key)`。
2. 与台账比对：
   - 预览对应的消息已在台账里 → 只更新未读，不建重复任务；
   - 新消息 → 建任务，状态 `new`。
3. 先写 `tasks.jsonl`，再尝试叫模型；写失败就不投递，下一轮重试。
4. 任务 id 一旦生成，后续所有回复、提醒、台账都带这个 id。

节流：

- 同一个群同一时刻最多一个活动任务；新消息追加到该任务。
- 全局活动任务上限（建议先 20），超过时按优先级/时间排序，不丢，只延后。
- 私聊/@ 优先于普通点名；逾期任务优先于新任务。

### 5.4 分步回复与回复台账

她这一侧新增/扩展的工具（名称暂定）：

| 工具 | 作用 |
|---|---|
| `her_inbox` | 看当前待回任务：群名、谁、什么时候、最后一句、状态、taskId |
| `wx_history` | 读某个群/某人的历史台账（分页、只读、过 guard） |
| `wx_reply` | 往任务对应的会话发一条；带 `task_id`，可多次调用；`final: true` 表示这条之后可以收尾 |
| `wx_task_done` | 明确结束任务；可写一句备注 |
| `wx_task_snooze` | 暂时不催，过多少分钟再看（例如等对方补充信息） |

发送流程：

1. `wx_reply` 校验 `taskId` 存在、属于当前会话、`chatId` 匹配。
2. 检查全名已解析；未解析直接拒绝，不按截断名发。
3. 过允许名单、@ 窗口、主机闸、说话频率（和现在一致）。
4. Actor 点开会话、核对、输入、回车、读回执。
5. 成功：追加出站台账，`replyCount++`，任务转 `replying` 或 `waiting`。
6. 失败/结果不明：任务标 `blocked` + `uncertain`，记录错误；**不自动重发**。
7. 同任务短时间内重复文本：拒绝并提示「这句刚发过」，除非显式 `allow_duplicate`（默认关闭）。

分步回复的语义：

- 一个任务可以有多条出站消息，不要求一次说完。
- `final: true` 不是必须的；如果她还在等对方补充，任务保持 `waiting`。
- 任务不会因为「发过一条」自动 `done`；只有 `wx_task_done` 或「对方明确结束/无需回复」的规则才收尾。
- 如果她在 `replying` 中途要查上下文，可以调 `wx_history`，不换任务。

### 5.5 不忘记回

三层保障：

1. **任务板**：所有待回都有状态和 `nextCheckAt`；逾期标红。
2. **每轮摘要**：她每轮 system prompt 里有一段动态 `fish:inbox`，只列未完成任务（最多 5 条），没有就空串。不把完整聊天记录塞进去。
3. **定时巡查**：每分钟检查一次任务板：
   - `overdue` 且未提醒 → 发一条宿主提醒（走 schedule，`source: schedule`，不冒充主机）；
   - 连续 N 次提醒仍无动作 → 标 `blocked`，在工作台显示「需要人处理」；
   - 不无限催，避免刷屏。

「不少回」的对账：

- 侧栏未读数 vs 台账最后一条：
  - 未读增加但台账没新增 → 触发 `captureChat`；
  - 台账有入站但任务板没有任务 → 补任务；
  - 任务 `done` 但又有新未读 → 新任务。
- 每次宿主重启、窗口恢复、树重建后都跑一次对账。

### 5.6 谁在找她

任务的 `requester` 必须回答三个问题：

1. **哪个会话**：全名 + `chatId`；群还是私聊。
2. **谁说的**：群成员显示名；私聊就是对方；识别不了写「未识别」。
3. **为什么找她**：`@` / 私聊 / 叫名字 / 回复她 / 明确提问。

`formatEarNote` 升级为任务摘要，例如：

```
[微信任务 t_01J...]
会话：星晓家园10号楼1302（群）
谁：安卓4224柚厨圣（@你）
时间：15:08
最后一句：「@D33P533K 给你充太多大白饭了，现在应该怎么削减」
未读：1
```

如果发言人未识别：

```
谁：群里有人（发言人未识别，置信度低）
```

不编造身份，不把侧栏里的其他名字当成发言人。

## 6. 与 dsh-fish 的边界

- **上下文归 dsh-wx。** 完整台账、目录、任务板都在 `~/.dsh-wx`；dsh-fish 不直接读这些文件，只通过窄接口拿摘要和分页历史。
- **人格归 dsh-fish。** 她仍然是同一个人；任务摘要走 system prompt 动态段，不写进事件流，不改变人设。
- **记忆归 dsh-fish。** 任务完成后，是否把这件事写进她的记忆，由她通过 `growth_commit` 决定；不自动把每条群聊写进 `events.jsonl`。
- **发送归 dsh-wx。** 所有发送仍过现有闸门；`wx_reply` 只是给 `wx_send` 加上 `taskId` 和绑定校验。
- **不加人格设置入口。** 这一阶段只加通道和任务能力，不加性格/好感度配置。

建议的宿主上下文段：

```
## 现在等你回的消息

- t_01J...｜星晓家园10号楼1302｜安卓4224柚厨圣 @你｜15:08
  「@D33P533K 给你充太多大白饭了，现在应该怎么削减」
  状态：未回｜已等 12 分钟
```

没有待办时这一段返回空串，不占 token。

## 7. 存储与保留

目录：

```
~/.dsh-wx/
  directory.json          # 会话目录快照（原子写）
  ledger/
    c_7f3a9d2e.jsonl      # 每群一本台账，append-only
  tasks.jsonl             # 任务状态迁移，append-only
  outbox.jsonl            # 发送意图 + 回执（排查重复/丢失）
  queue-state.json        # 可选：租约/游标快照，坏了可从 tasks 重放
```

约束：

- 全部 `0600`；不写 cookie、token、密码。
- 台账不删行；纠错用追加 `repair`。
- 保留策略默认：任务记录永久保留；消息台账保留 90 天，之后归档到 `ledger/archive/`，不静默删除。
- 大文件分段：按 `chatId` + 月份分文件，避免单文件无限增长。
- 所有对外返回的历史文本过 `guard.js`；私聊内容不套公开评论区的 `looksLikeLeak`，但凭据/注入行仍要拦。

## 8. 分阶段实施

### 阶段 1：请求池 + 目录 + 回复台账（P0）

范围：

- `scanDirectory()`：侧栏滚动枚举、全名解析、别名合并。
- `TaskBoard`：任务落盘、状态机、入池、去重、租约、重启恢复。
- 耳朵 v2：从「合并通知」改为「每个请求一个任务」；投递任务摘要。
- `her_inbox` / `wx_task_done`；`wx_send` 增加可选 `taskId`。
- 未读对账；逾期巡检（先只工作台显示，不自动催）。

验收：

- 100 个会话的 fixture 能完整枚举，不重复、不丢。
- 截断名/同前缀群不会误发；未解析时拒绝发送。
- 宿主重启后待办不丢；已发送的不重复发。
- 侧栏有新未读但任务板没有 → 自动补任务。

### 阶段 2：完整上下文 + 发言人（P1）

范围：

- `captureChat()`：消息区滚动回溯、重叠去重、台账追加。
- `wx_history`：分页读取，过 guard。
- 发言人识别：增强 `wx-elements.mjs` 输出消息子树；OCR 兜底；置信度落盘。
- 任务摘要带最近上下文和发言人。

验收：

- 连续 3 屏消息能按顺序入账，无重复、无倒序。
- 同一群里两个人交替说话，能区分；识别不了时明确标「未识别」。
- 她回话时能引用前文，不只看最后一条预览。

### 阶段 3：分步回复 + 不忘记回（P2）

范围：

- `wx_reply(taskId, text, final?)` 多次发送、绑定任务。
- `wx_task_snooze` / `wx_task_done`。
- 逾期提醒、连续提醒上限、工作台任务板。
- 发送结果 `uncertain` 的处理流程（人工确认，不自动重发）。

验收：

- 一个任务回 3 条，台账 3 条出站都挂同一个 taskId。
- 回了半句后任务仍是 `waiting`，不会被当成 `done`。
- 逾期任务在工作台可见，并按策略提醒一次；不会无限刷屏。

### 阶段 4：按需并行（P3，暂不做）

只有在阶段 1–3 的指标证明「单会话排队是瓶颈」时，才考虑：

- 一个 chat 一个 session；
- GUI Actor 单写者；
- 每 session 绑定 chat；
- 全局并发上限 2；
- 记忆单写者、per-session wake。

这一阶段的前置条件、风险和收益见上一轮调研结论；本文档不展开实现。

## 9. 验收标准（整体）

1. **不丢**：任意时刻 kill 宿主，重启后未完成任务仍在；入站消息不因模型失败丢失。
2. **不重**：同一入站消息不会生成两个任务；同一任务不会因为重试自动重复发送。
3. **不忘**：超过 `nextCheckAt` 的任务进入逾期视图；每轮摘要能看到；有提醒上限。
4. **不少回**：侧栏未读与台账/任务对账，发现缺口能自动补。
5. **知道是谁**：每个任务有会话全名 + 发言人 + 找她的原因；未知时明确标注。
6. **全名发送**：截断名/歧义名不能作为发送目标；发送前再次核对当前会话。
7. **上下文**：每个群有独立台账；能回溯至少 N 屏；出站也入账。
8. **分步**：同一任务可多次回复；任务完成由显式动作决定。
9. **可观测**：工作台能看到队列、状态、最后错误、发送回执。
10. **测试**：目录/台账/任务状态机/去重/重启恢复都有 `node:test` 或现有 standalone 测试；真机微信 E2E 需单独批准。

## 10. 风险与待定

| 问题 | 现状/风险 | 建议 |
|---|---|---|
| 发言人识别 | 树目前只有正文；OCR 不一定准 | 先增强树子树输出；识别不了就标未知，不猜 |
| 长名字全名 | 打开会话/信息面板才能拿全名 | 懒解析 + 歧义隔离；未解析禁止发送 |
| 历史回溯 | 微信可能不加载更早消息 | 设最大回溯页数；到顶就停，不假装有全文 |
| 重复发送 | 微信无出站消息 id | 出站 intent + 回执；`uncertain` 不自动重发 |
| 存储增长 | 全量台账会很大 | 按群/月分段；90 天后归档，不删除 |
| 隐私 | 群聊含别人的信息 | 本地 0600；不写日志到 stdout；不把原文塞进 system prompt |
| 请求范围 | 所有群消息都建任务会爆炸 | 只对私聊/@/点名/回复建任务；其余只进上下文 |
| 模型成本 | 任务摘要 + 上下文会增加 token | 摘要限条数；历史按需读取；不做每轮全量注入 |
| 并行 | 单会话可能成为瓶颈 | 先做 P0–P2；用指标决定是否上 P3 |

待你确认的产品问题：

1. 「请求」的范围：只回私聊/@/点名，还是允许名单里的所有未读都建任务？
2. 群聊上下文保留多久：90 天是否合适？
3. 逾期提醒的节奏：例如 15 分钟、1 小时、4 小时各一次，之后标「需要人处理」？
4. 工作台任务板放在现有「大肥鱼的家」页面里，还是单独一页？

## 11. 明确不做

- 不做微信协议端，不依赖 NapCat 之类的外部服务。
- 不把完整聊天记录写进 `events.jsonl` 或人设。
- 不用截断名、前缀匹配、模糊匹配发送。
- 不自动回复所有群消息。
- 不在发送结果不确定时自动重发。
- 不删除台账或历史事件。
- 不为了并行而先拆多窗口；GUI 始终单写者。
