# 大肥鱼微信工具聚合与渐进式披露方案

日期：2026-11-06
状态：方案比较；尚未选型或实施

## 1. 背景与目标

大肥鱼当前拿到的微信工具及其说明占用较多对话上下文。上下文持续放着大量界面操作步骤、低频工具参数和重复安全说明，会让模型更像在照流程操作，挤压她自然理解和回应主机的空间。

本设计比较三种工具架构，分别优先优化：

1. **上下文占用**：常驻工具 schema 和说明尽可能少，按需要再取目录和用法。
2. **人设遵循**：常见对话意图直接可用，减少每次先查目录的机械感，同时移除低频原语的噪声。
3. **实施时间**：尽量不改现有执行链路，先以较小改动提供按需帮助。

目标不是单纯降低工具数量。需要减少每次模型请求中常驻的工具 schema 和重复说明，同时保持常见工作流顺手、关键发送边界不变。工具清单变短本身不能保证人设表达改善；提示词、工具返回和历史内容仍可能占用大量上下文。

## 2. 已知基线与约束

### 2.1 工具数量

截至本设计日期，所核对的源码快照如下：

| 工作区 | 分支 / 提交 | WX 注册入口 | WX system prompt 所写数量 |
| --- | --- | ---: | ---: |
| 主工作区 | `main` / `810beb1` | 14 | 与 dev 版本不同 |
| 开发工作区 | `dev` / `483b8c8` | 18 | 15 |

因此，后续方案估算以 dev 的 18 个入口为例，不把入口数当作跨分支常量。实施前需要再次盘点将要修改的分支，并同步修正文案与真实注册集合。

dev 的 18 个入口由 11 个微信常用 / 操作工具和 7 个表情工具构成：`wx_see`、`wx_peek`、`wx_click`、`wx_type`、`wx_send`、`wx_context`、`wx_history`、`wx_task_snooze`、`wx_task_done`、`wx_ocr`、`wx_key`，以及 `wx_sticker_scan`、`wx_sticker_list`、`wx_sticker_find`、`wx_sticker_tag`、`wx_sticker_send`、`wx_sticker_collect`、`wx_sticker_search`。

### 2.2 宿主工具接口

当前运行宿主为 `dsh-tools 0.2.1-rc.5`。核对到的接口行为是：

- `tools.register` 注册固定工具 schema。
- `tools.restrict` 能按 agent 收窄可见工具集合。
- 当前接口没有逐轮动态替换已注册工具 schema 的能力。

所以，“先只暴露一个入口”需要注册一个 dispatcher，由它在插件内部路由到已有业务逻辑；目录和详细用法可以作为调用结果按需返回。仅仅新增目录工具不会隐藏已有工具 schema。

### 2.3 必须保持的发送边界

- 普通 `wx_send` 继续执行当前会话、允许会话、主机意图、@ 条件和发送频率检查。
- 提醒 permit 只绕过主机意图与 @ 闸；仍绑定原会话和原文、一次性使用，并继续经过会话及频率相关检查。
- 表情发送继续执行现有会话和发送校验；不因 dispatcher 或工具聚合降低校验强度。
- 聚合入口必须复用现有业务函数和授权路径，不能从 dispatcher 内部直接绕过原有检查。

## 3. 方案一：上下文最优，单一 dispatcher

### 架构

微信侧只向模型暴露一个紧凑的入口，例如 `wx`。该入口接收通用操作字段和参数对象，在插件内部处理三种请求：

- `catalog`：返回能力分类和每项一句话摘要。
- `describe`：返回某个操作的完整参数、限制和适用条件。
- `call`：执行已注册的操作，并返回原工具结果。

示意流程：

```text
模型请求只带 wx schema
  → 需要微信能力时请求 catalog
  → 对陌生或低频操作请求 describe
  → 用 call 执行具体动作
```

可把操作分成“读消息 / 查历史 / 发送 / 任务 / 界面 / 表情”等类别。目录结果先给类别和短摘要，避免首次披露全部参数细节；详细参数只在 `describe` 结果里出现。

### 渐进式披露

1. 常驻上下文只有 `wx` 的参数 schema 和极短的导航说明。
2. 需要微信能力时才读取目录；用户直接要求熟悉的高层动作时，也可以跳过目录直接调用已知动作。
3. 只有参数或操作语义不明确时才取详细说明。
4. 工具执行后才把必要的结果带回上下文。

### 优点

- 常驻的微信工具 schema 数可以从 18 降为 1，是三案中上下文压缩空间最大的方案。
- 低频操作的完整说明不会在每轮请求中重复出现。
- 目录、说明和执行可以统一观测，便于统计哪些能力确实被使用。

### 代价与风险

- 不熟悉的操作至少增加目录或说明往返；如果必须先查目录再执行，工具调用数和延迟会增加。
- 通用 `input` 对象难以表达并校验每个操作自己的精确 JSON Schema；参数错误可能从模型侧验证转移到插件运行时。
- 模型要记住 dispatcher 协议。若协议过于抽象，使用体验会变成“先操作工具来找工具”。
- 内部调用既有能力时要核实宿主对取消、超时、错误和调用记录的处理；不能假设在工具 handler 中再调用另一个已注册工具会自动经过同样的宿主中间件。
- `catalog`、`describe` 的返回内容和执行历史也占上下文，披露过多会抵消 schema 节省。

### 工作量与适用情况

工作量：**大**。需要整理工具目录、抽出可由 dispatcher 调用的内部业务函数、定义参数校验和错误契约，并补充调用路径测试。

适合把常驻上下文压缩放在第一位，并能接受陌生或低频能力多一次交互的场景。

## 4. 方案二：人设遵循最优，常用工具直达、低频操作聚合

### 架构

常见、高意图的动作保留独立工具，让大肥鱼收到对话后可以直接理解和行动；低频、机械、参数细碎的操作合并到少数类别入口。

按 dev 的 18 个入口，示例保留以下 9 个直达工具：

- 对话和查阅：`wx_peek`、`wx_context`、`wx_history`
- 回复与任务：`wx_send`、`wx_task_snooze`、`wx_task_done`
- 表情沟通：`wx_sticker_find`、`wx_sticker_send`、`wx_sticker_search`

其余入口聚合成两个类别工具：

- `wx_ui`：承载 `wx_see`、`wx_click`、`wx_type`、`wx_ocr`、`wx_key`，供需要界面级操作时使用。
- `wx_sticker_library`：承载 `wx_sticker_scan`、`wx_sticker_list`、`wx_sticker_tag`、`wx_sticker_collect`，供收藏索引维护和收藏操作使用。

这样 dev 示例从 18 个 schema 降到约 11 个。归并的是入口，不是删除能力；每个类别入口内部仍调用原有实现和检查。

### 渐进式披露

1. 常驻上下文包含常见对话工具和两个短类别入口。
2. `wx_ui` 的说明只写“用于低层界面操作，提供截图、点击、输入、OCR 和按键”，不在 system prompt 展开每个动作的长流程。
3. 类别入口接受简短 `action` 和参数；模型需要低频动作时，从简短说明或按需帮助结果取得完整参数用法。
4. 工具自身 description 保留模型安全决策必需的信息；冗长的重复操作教程和已由代码强制执行的细节不再在 prompt 中重复。

### 优点

- `wx_peek`、`wx_send`、上下文查询、任务处理和常用表情动作仍然可以直接选择，减少为了普通交流先查目录的步骤。
- 相较单 dispatcher，日常工具名和参数 schema 仍有较强语义提示，有利于模型根据对话自然选择工具。
- 低层 UI 原语和表情索引维护不再各占一个独立 schema；system prompt 也可以从逐项说明改为短导航。
- 入口数量和常驻上下文得到实质压缩，改造范围仍可拆成小步验证。

### 代价与风险

- 仍有约 11 个工具 schema 常驻；压缩幅度低于单 dispatcher。
- 类别工具要设计 `action` 与参数约定。若把动作说明全塞回 schema description，收益会变小；若说明过短，低频操作可能需要额外读取帮助。
- `wx_ui` 中的输入、按键和截图等操作仍需清楚提示边界，避免模型把低层发消息路径当成普通回复首选。
- `wx_sticker_library` 包含本地索引维护和微信收藏操作，说明必须区分纯本地变更与会操作界面的动作。

### 工作量与适用情况

工作量：**中**。先提取 `wx_ui` 和 `wx_sticker_library` 共用 handler，再注册聚合入口并移除对应原始注册；同步精简 prompt。可分模块实现和回归。

适合首要目标是让大肥鱼更像在正常对话，同时确实减少工具清单噪声，并希望控制改造成本的场景。当前三案中，它是“留出人设发挥空间”与常见工作流顺手之间的折中候选，但尚未定案。

## 5. 方案三：时间最优，保留直达工具并增加目录 / 按需帮助

### 架构

保留所有现有 WX 工具和执行路径，新增一个只读 `wx_help` 或 `wx_catalog` 工具。模型可按需查询分类、用途和详细参数；system prompt 则缩短为简短导航，减少与工具 description 的重复解释。

### 渐进式披露

1. 18 个现有工具 schema 仍然直接可见，熟悉的动作照常调用。
2. 模型不确定工具用途或参数时，调用 `wx_help` 查询单项说明或分类目录。
3. 返回值只包含请求的那一类说明，不一次性输出完整手册。

### 优点

- 对现有执行路径影响最小，风险和实现成本最低。
- 不需要把复杂的工具调用转发逻辑塞进 dispatcher，现有独立 schema 继续提供参数校验。
- 可以先收集工具调用和帮助查询数据，为之后是否聚合提供依据。

### 代价与风险

- 所有 18 个 schema 仍然进入模型请求；新增目录工具反而增加一个 schema。
- 只有精简 system prompt 后，重复文字部分会减少；工具 schema 本身仍常驻，不能达到真正的工具渐进披露。
- 如果详细说明在 WX prompt、工具 description 和 `wx_help` 中重复维护，会产生内容漂移和额外维护负担。
- 因而这是低风险过渡方案，不足以单独实现“显著降低一次对话直接塞进上下文的工具和工具说明”这一目标。

### 工作量与适用情况

工作量：**小**。新增只读帮助查询并整理 prompt，不改当前工具注册和执行流程。

适合想快速验证说明去重和查询体验、暂时不接受工具路由改造的场景。若选择此案，验收目标应明确为“降低重复 prompt 文本”，不能报告成“减少了常驻工具 schema”。

## 6. 横向比较

| 方案 | 常驻 WX schema（dev 示例） | 常见动作是否直达 | 低频说明披露 | 实施工作量 | 主要代价 |
| --- | ---: | --- | --- | --- | --- |
| 1. 单 dispatcher | 1 | 否，通常先目录 / 说明 | 工具结果按需披露 | 大 | 额外往返，通用参数校验较弱 |
| 2. 直达 + 类别聚合 | 约 11 | 是 | 类别工具按需提供细节 | 中 | 仍有多个常驻 schema，需维护聚合参数 |
| 3. 目录 + 原工具 | 19（原 18 + 目录） | 是 | 说明按需，原 schema 仍常驻 | 小 | schema 上下文没有下降 |

三种方案都应缩短 WX system prompt 的重复清单和教程，并把说明维护成单一来源。对安全校验已由代码强制执行的部分，可以减少重复叙述；模型做动作选择所必需的关键限制仍要在合适的位置清楚表达。

## 7. 评估与验收建议

实施前先记录当前 main 或 dev 实际送入模型请求的 WX 工具 schema 和 WX prompt token 数，避免只用源码行数推断上下文收益。实施后在同一组任务上比较：

- 常驻 WX schema 的数量及 token 数、WX prompt token 数。
- 普通消息回复、查上下文、处理提醒、发送收藏表情、界面异常排查等任务的成功率和工具调用轮数。
- 是否出现不必要的目录 / 帮助查询、参数错误、重复调用或错误会话发送。
- 对相同对话样本盲评其回应是否自然、是否贴合大肥鱼既有语气，而不只看工具调用是否成功。

单纯减少工具数量或 token 数不算完整验收；若常见交流因此多出工具往返，或表达更像操作手册，应调整类别边界或回退对应直达入口。

## 8. 待决事项

- 最终以 main 还是 dev 作为实施和验收基线；实施前重新盘点入口及 prompt 数量。
- 三个优化目标中哪个是首要目标。若首要目标是常见交流自然、又要明显压缩上下文，优先评估方案二；若允许常见动作多一次工具往返并以最小 schema 为先，再评估方案一。
- `wx_sticker_search` 是否保持直达。它是高意图表达能力，但会直接发送盲选结果，需要结合实际调用频率和安全评估决定。
- 类别工具是否以精确 action schema 暴露动作，还是使用通用 action 字段并提供按需帮助；此选择影响 schema 大小、参数校验和调用轮数。

**当前没有选定方案，也没有实施任何工具注册、提示词、配置或运行环境改动。**
