# 桌宠新动作与事件链设计（分两期）

> 状态：一期设计已补全，待复审；二期仍是方向稿。未实现。
> 背景：上游 `PC2005-cloud/dsh-pet` v0.4.9 有 114 段动画和睡觉、余额、碎碎念、节日、玩耍等状态。我们的壳只有 11 段动画、14 个槽位和六档活动。
>
> **分期：**
> - **一期（播放层）**：「演一个动作」能播全部新动作，并支持用户注册新动作后立即演出。不接事件。
> - **二期（事件链）**：事件触发动作。「演一个动作」里的动作总数可以多于事件能触发的动作数。
>
> 评审需求清单：[2026-11-17 需求列表](../reviews/2026-11-17-diegetic-feedback-and-pet-requirements.md)。

## 0. 两期的边界

| | 一期 | 二期 |
|---|---|---|
| 目标 | 手动演得出来 | 事件驱动演得出来 |
| 入口 | 右键「演一个动作」、托盘、`/pet/act` | 会话事件、她的发言、作息、日期 |
| 动作清单 | 全部素材，可扩展 | 其中一个子集有触发条件 |
| 改 `dsh-fish` | 改动作协议与内存状态（`pet-view.js`、`observe.js`），不接事件源 | 改事件接线与 `/pet/state` 增量字段 |
| 改桌宠壳 | 改 | 改 |
| 播放层 | 本期打通 | 沿用 |
| 风险 | 播放层，已验证大半 | 事件源，未验证 |

**二期的核心约束：** 动作清单（手动可演）和触发表（事件可触发）是两张独立的表。一个动作没有任何触发条件，也照样出现在菜单里。这样新增素材不需要同时设计触发。

### 0.1 已确认决策

2026-11-17 评审确认：

1. **动作重载：** 一期只做菜单里的手动“重新载入动作”，不监听文件变化。
2. **常用菜单：** “常用”保留现有 7 项；其余 7 个播放槽动作放到“状态”分组，14 个槽仍全部可用。
3. **未登记素材：** 本期不做自动发现；`webm/` 里有文件但没有 `actions.json` 条目时，菜单不出现，也不要求改名或补猜。
4. **循环动作：** `loop:true` 是持续手动状态，不会自动结束；新动作、拖动或“停下当前动作”可以抢占/结束，不能依赖“播完恢复”。
5. **presence：** 二期保留现有 `presence.on → thinking` 稳态；新增事件链不能把它删掉。
6. **休息：** 二期的稳态来源以日程窗口 A 为主，保留菜单手动“睡觉/起来”C；不做空闲超时 B。
7. **休息交互：** 点击休息中的桌宠显示固定短句“在休息”，不调用模型。
8. **说话气泡：** 使用已发生原话的截断版本，短 TTL；桌宠不生成新文案。
9. **余额：** 不做。

## 1. 原则

1. **动画由机械事件决定，不由模型决定。** 桌宠不调模型，不生成文字。
2. **不引入上游的人设、对话、记忆。** 只借动作表现，上游的台词配置不搬。
3. **易失，不落盘。** 沿用 `pet-view.js` 约定：不写 `events.jsonl`，不写台账。
4. **素材不进 Git。** 沿用 `assets/webm/` 本地同步。素材为 CC BY-NC-SA 4.0，非商业。
5. **注册一个动作 = 加数据，不改代码。** 一期的验收标准之一。

## 2. 现状与已验证的事实

### 2.1 现状

```
菜单「演一个动作」(menu-model.ts 硬编码 7 项)
   → actions.motion('waving')  → IPC pet:action
   → App.tsx performedMotion() → pet.motion({type, loop:false, replay:true})
   → dsh-pet-component：type 只能是 14 个名字之一
   → skin.json 的 motions[type] → webm 文件名
```

限制：

- 菜单固定 7 项，14 个槽也只暴露了 7 个。
- 槽位固定 14 个，一个槽一个动画（或一个候选池，随机抽）。
- `skin.ts` 的 `MOTIONS` 常量也固定为 14 个。皮肤校验要求这 14 个都存在。

### 2.2 已验证（读了 `dsh-pet-component` 0.2.5 的类型与产物）

1. `pet.motion({ type })` 的 `type` 类型是 `PetRenderMotion = Motion | 'dragging'`，`Motion` 是 14 个名字的联合。**组件不接受自定义动作名。**
2. 动作名到动画名的解析在 `resolveDshAnimation`：先查 `config.motions[type]`，再查 `config.animations.motions[type]`，再查协议池，最后回落 idle。
3. `config.motions[type]` 的值是 `string | string[]`，数组等概率随机抽一个，且会避开上一次的结果。
4. 视频地址由 `uri` 加动画名加扩展名拼出，名字经过 `encodeURIComponent`，所以中文名可用。
5. 组件的循环语义由动作名决定（`isLoopingMotion`）。`waving`、`success`、`error` 等是播完回落，`idle`、`working`、`thinking` 等循环。**`loop: false` 可以由我们在调用时显式给出**，所以任何动画都可以被当作一次性播放。
6. 皮肤切换已经是运行时行为：渲染进程收到新的 config 和 uri 就换，不需要重启。

### 2.3 未验证

- **`config` 在不换 `Pet` 实例的情况下被替换时，进行中的动画是否会被打断或残留。** 一期方案依赖在播放前改写 config，要实测。
- 114 个 webm 是否都带透明通道。
- 节日类等素材是否都在同一授权声明下。
- 动画名里带空格或特殊字符的文件，在 `pet-asset://` 协议里能否正常取到。

## 3. 一期：打通播放层

### 3.1 要解决的问题

组件只有 14 个动作名，素材有 100 多段。要让"演一个动作"能播任意一段，并且新增素材不改代码。

### 3.2 方案：动作槽是播放通道，不是动作本身

把组件的 14 个槽位看作 **播放通道**。我们自己维护一张 **动作注册表**（动作 id → 动画名 + 播放方式）。演一个动作时：

1. 查注册表，得到动画名和播放方式（一次性或循环）。
2. 选一个**借用槽**（例如 `waving`），把 `config.motions[借用槽]` 临时指向这个动画名。
3. 调 `pet.motion({ type: 借用槽, loop: 注册表指定, replay: true })`。
4. 播完后恢复该槽原本的映射，回落稳态。

借用槽在一次性演出期间被占用；持续动作会一直占用到被停止或被新动作抢占。稳态（idle、六档活动、presence）用的是它们自己的槽，不受影响，但恢复映射必须通过下面的状态机完成。

**为什么不 fork 组件：** 组件是 MIT，可以改，但改了就要自己维护一份，升级成本高。借用槽方案只用组件的公开 API。

**这个方案的前提就是 §2.3 第一条。** 如果实测发现换 config 会打断正在播的稳态动画或闪烁，退路是：

- **退路 A：** 给每个借用槽预先写入"动画池"，演出时只做 `pet.motion`，不改 config。代价是池里所有动画要在皮肤加载时就声明。
- **退路 B：** 自己在组件之上叠一个 `<video>` 播放层，只用于"演一个动作"，播完撤掉。代价是要自己处理透明、位置、层级、点击穿透。

### 3.2.1 播放状态机

借用槽不能只靠“调用后延时恢复”实现，否则循环动作和连续点击会互相覆盖。播放层必须维护一个单独的手动动作状态：

| 状态 | 含义 | 进入 | 退出 |
| --- | --- | --- | --- |
| `idle` | 没有手动动作，跟随稳态 | 启动、动作结束、停下 | 用户演出动作、cue/菜单命令 |
| `playing-once` | 一次性动作正在播放 | `loop:false` 的动作 | 收到完成信号、被新动作抢占、skin 失效 |
| `playing-seq` | 顺序动作正在逐段播放 | `seq` 动作开始 | 最后一段完成、被新动作抢占、错误 |
| `holding-loop` | 循环动作保持中 | `loop:true` 的 `anim`/`seq` 最后一段 | “停下”、新动作、拖动抢占、skin 失效 |
| `restoring` | 正在恢复被借用的映射 | 任何结束路径 | 恢复成功回到 `idle` |

实现约束：

- 每次手动动作分配一个单调递增的 `actionGeneration`；旧动作的完成/恢复回调只有在 generation 仍等于当前值时才有效，防止连续点击时旧回调覆盖新动作。
- `playing-once` 使用组件已有的 `onMotionChange` / `onAnimationChange` 判断一次性段结束；不靠猜测视频时长。若组件回调不可用，方案必须回到 §2.3 的实测 Gate，不能静默用固定延时。
- `playing-seq` 在一次段结束后启动下一段。最后一段是 `loop:true` 时转入 `holding-loop`；否则播完后恢复映射并回到 `idle`。
- `holding-loop` 不自动恢复映射。菜单新增“停下当前动作”，内部调用 `pet.clear()` 或等价命令，恢复借用槽和稳态。
- 新动作先使旧 generation 失效，再更新借用槽并启动；拖动和皮肤切换也走同一抢占路径。
- 如果动作在恢复前收到新的 activity/presence 更新，保存最新稳态，但不要用旧动作的完成事件覆盖它；恢复完成后只回落到最新稳态。
- 同一时刻只允许一个借用槽。出现并发动作时，后到动作胜出；被取消的动作不写日志到事件流，只写本地调试日志。

### 3.3 动作注册表

文件：`assets/actions.json`（默认皮肤）与 `assets/skins/<id>/actions.json`（皮肤覆盖）。

```jsonc
{
  "actions": [
    { "id": "kick-shuttlecock", "label": "踢毽子",   "anim": "踢毽子",   "group": "玩耍" },
    { "id": "swing",            "label": "荡秋千",   "anim": "荡秋千",   "group": "玩耍" },
    { "id": "sleep",            "label": "睡觉",     "seq": ["睡觉-开始", "睡觉-循环"], "loop": true, "group": "休息" },
    { "id": "wake",             "label": "起来",     "anim": "睡觉-起来", "group": "休息" },
    { "id": "xmas-tree",        "label": "装点圣诞树","anim": "装点圣诞树", "group": "节日" }
  ]
}
```

字段：

| 字段 | 必填 | 含义 |
|---|---|---|
| `id` | 是 | 小写字母、数字、连字符，1–32 位，与皮肤 id 同规则 |
| `label` | 是 | 菜单显示名 |
| `anim` | 二选一 | 单个动画名，对应 `webm/<名>.webm` |
| `seq` | 二选一 | 多段顺序播放，用于睡觉三段式 |
| `loop` | 否 | 默认 `false`。`seq` 的最后一段循环 |
| `group` | 否 | 菜单分组，缺省为"其他" |

校验规则沿用皮肤校验的口径：

- `anim` 与 `seq` 引用的 webm 必须存在，不存在的动作整条丢弃并记一条日志，**不拒绝整个文件**。这与现有皮肤"14 个缺一个就拒绝"不同，因为注册表是开放集合，缺一个不应该让其他动作失效。
- `id` 重复时后者覆盖前者，皮肤文件覆盖默认文件。
- 路径穿越防护沿用 `isInside` 检查。

### 3.4 注册新动作

**用户的操作：**

1. 把 `xxx.webm` 放进 `assets/webm/`（或皮肤的 `webm/`）。
2. 在 `actions.json` 里加一条。
3. 菜单点「重新载入动作」。重新载入成功后立即发一次 `hello`，让 `/pet/act` 的新 id 校验同步生效。

不改代码，不重新编译。

**自动发现：** 本期不做。未登记的 webm 不进入菜单、不被 `/pet/act` 接受；用户必须显式登记，避免文件名、皮肤和动作 id 三套命名混在一起。

### 3.5 菜单

「演一个动作」子菜单改为按 `group` 分组的二级菜单。动作数量多，一级平铺不可用。

```
演一个动作 ▸
  常用 ▸        挥手  思考  忙碌 …           （原 7 项保留）
  状态 ▸        转身  走开  跑动 …           （其余播放槽动作）
  玩耍 ▸        踢毽子  荡秋千 …
  休息 ▸        睡觉  起来
  节日 ▸        装点圣诞树  讨糖南瓜灯 …
  停下当前动作
  重新载入动作
```

「常用」组保留现在的 7 项，行为不变；其余 7 个播放槽动作放进「状态」，不减少现有 14 槽的可达性。

### 3.6 IPC 与协议

- `pet:action` 的载荷从 `motion: string` 扩展为 `{ motion: string } | { action: string }`。老载荷继续有效。
- `POST /pet/act` 同样接受 `action: <id>`，由 `pet-view.js` 校验 id 是否存在。**一期不让服务端知道动作清单**：桌宠 `hello` 时上报已注册的动作 id 列表（与现在上报皮肤列表同一机制），`/pet/act` 按这个列表校验。
- `hello` 增加 `actions: [{ id, label, group }]`。
- `action` 必须是最近一次成功 `hello` 上报的 id；没有 `actions`、id 为空或未知时返回 400，不回落到猜测的动画名。`motion` 仍只接受现有 14 个槽名。
- `hello` 的 actions 去重后按 id 排序，最多 256 条；重复 id 以最后一次上报为准，避免皮肤切换时短暂出现两套清单。

### 3.8 一期验收

## 4. 二期：事件触发动作

### 4.1 前提

一期完成后，「演一个动作」里有 N 个动作。二期只给其中 M 个（M ≤ N）配触发条件。**没有触发的动作继续只能手动演。**

### 4.2 触发表

触发表是一张独立的数据，不与动作注册表合并：

```jsonc
// assets/triggers.json
{
  "triggers": [
    { "when": "activity:success",    "pool": ["success-cheer"], "once": true },
    { "when": "speak",               "pool": ["mutter-daze", "mutter-screen", "mutter-wipe"], "w": [3, 3, 1] },
    { "when": "bili_replied",        "pool": ["happy-bounce"] },
    { "when": "scene:rest:enter",    "pool": ["sleep"] },
    { "when": "scene:rest:exit",     "pool": ["wake"] },
    { "when": "ambient",             "pool": ["kick-shuttlecock", "swing"], "minGapSec": 300 },
    { "when": "date:12-25",          "pool": ["xmas-tree"], "inAmbient": true }
  ]
}
```

- `pool` 里的是动作 id。池里多于一个就按权重抽。
- 触发指向不存在的动作，该条丢弃并记日志，沿用一期的"开放集合"口径。
- **不在触发表里出现的动作不报错**，这是设计，不是遗漏。
- 同一事件有多条可用 trigger 时，按 `triggers` 文件顺序取第一条；池内再用可注入随机源按 `w` 选择。这样重放结果可复现，也给皮肤作者明确的覆盖顺序。
- `w` 必须与 `pool` 等长、全为非负有限数且总和大于 0；缺省时等权。
- 皮肤 `assets/skins/<id>/triggers.json` 与默认触发表按 `when` 合并；同一 `when` 由皮肤条目覆盖默认条目，不在默认表中出现的皮肤条目追加在末尾。
- `once:true` 表示每次事件发生只触发一次。活动/场景 trigger 以状态切换作为一次发生；date trigger 以每个本地日期第一次进入可触发状态作为一次发生。
- `inAmbient:true` 表示该 trigger 只在没有 scene、activity、presence 和手动动作时参与匹配；它不会在活动中途插播。

### 4.3 三层模型

桌宠每拍把当前状态归约为三层，优先级从高到低：

1. **环境层（scene）**：休息、出门。互斥，决定稳态。
2. **活动层（activity）**：六档，沿用 `waiting > error > working > thinking > result > success`。
3. **基础层（presence/idle）**：没有 scene/activity 时，`presence.on` 仍显示 `thinking`，否则 `idle`。
4. **闲置层（ambient）**：只有 scene、activity、presence 和手动动作都不存在时，才按权重随机插播。

稳态完整优先级为：`waiting > scene(rest/out) > 其他 activity > presence:on → thinking > idle`。这保留了现有 presence thinking 行为；如果 presence 与 rest 同时存在，rest 优先。一次性 cue 和手动动作叠加在稳态上，播完回落到当时最新的稳态。休息期间点击显示固定短句，聊天 cue 仍可播放配置动作，但不改变 `scene`。

### 4.4 协议增量

`/pet/state` 增量扩展，旧字段不动：

```jsonc
{
  "activity": { ... },                           // 不变
  "action":   { ... },                           // 不变，保留给菜单与 /pet/act
  "scene":    { "kind": "rest", "at": 0 },       // 新增，null = 无
  "cues": [                                       // 新增，一次性事件，按 id 去重
    { "id": "cue-…", "kind": "speak|replied", "text": "…", "at": 0, "ttlMs": 15000 }
  ]
}
```

- `cues` 是环形缓冲，最多 8 条，每条带 ttl，桌宠记住已播的 id。
- `text` 只允许来自已发生的事实（她说的话的摘要），桌宠侧不拼文案。
- 触发表在**桌宠侧**解析：服务端只报事实（发生了什么），不决定演哪个动作。这样换皮肤就换表现，服务端不用知道素材。

### 4.6 休息的来源（已定）

- **A. 日程窗口。** `scheduler.js` 已有 `inWindow`，窗口外 = 休息。真实、无新状态，但要核实窗口是否表达"她在睡"。
- **B. 空闲超时。** 无事件超过 N 分钟即休息。简单，白天会误睡。
- **C. 手动。** 菜单"睡觉/起来"。一期已经有。

采用 A 为主、C 保留为覆盖，B 不做。日程窗口只决定默认 scene；手动“起来”在当前窗口内覆盖为清醒，手动“睡觉”在窗口外也可进入 rest，但需要下次日程 tick 或用户操作清除覆盖。覆盖状态易失，不写事件流。
